## O que entregar

O RH cadastra as pessoas que usam o sistema e as ativa ou desativa:

- Módulo `users/` com `GET /users` (filtros `role`, `status`, `search`; ordem alfabética por nome), `POST /users` e `PATCH /users/:id/status`, todas `@Roles("HR")` (o `ADMIN` herda). Formatos da spec.
- `POST /users` com `role` `THERAPIST` cria o perfil de massoterapeuta junto, na mesma transação.
- E-mail válido e único (409 com `userEmailAlreadyExists`).
- Auditoria: `USER_CREATED`, `USER_ACTIVATED` e `USER_DEACTIVATED`.
- Remover `GET /admin/users`, `POST /admin/users` e `PATCH /admin/users/:id`; a linha "legacy admin" da matriz de permissões passa a usar uma rota que continua no legado.
- Linhas novas na matriz de permissões.

Fora deste ticket: exclusão de usuário, login Google e `googleSubject`.

## Critérios de aceite

- [x] **Dado** o RH identificado, **quando** envia `POST /users` com dados válidos e `role = THERAPIST`, **então** o usuário é criado `ACTIVE`, o registro em `Therapist` é gerado e há um `AuditEvent` de criação.
- [x] **Dado** um e-mail já usado, **quando** o RH cria outro usuário com ele, **então** responde 409 com `userEmailAlreadyExists` e nada é gravado.
- [x] **Dado** usuários de vários papéis, **quando** o RH chama `GET /users`, **então** recebe a lista em ordem alfabética, e os filtros `role`, `status` e `search` restringem o resultado.
- [x] **Dado** um colaborador `ACTIVE`, **quando** o RH envia `PATCH /users/:id/status` com `INACTIVE`, **então** ele passa a `INACTIVE`, some de `GET /auth/demo-users` e recebe 401 na próxima requisição.
- [x] **Dado** um usuário `INACTIVE`, **quando** o RH o reativa, **então** ele volta a `GET /auth/demo-users`.
- [x] **Dado** um colaborador ou massoterapeuta, **quando** chama qualquer rota de `/users`, **então** responde 403 (matriz de permissões).
- [x] `GET /me` e `GET /auth/demo-users` continuam com o contrato do EP-02 (os testes deles passam sem alteração).
- [x] `npm run test`, `npm run test:e2e`, `npm run lint` e `npm run build` passam.
