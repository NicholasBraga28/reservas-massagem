## O que entregar

Os parâmetros das regras de negócio passam a ser guardados no banco. Num banco novo, a aplicação grava sozinha os valores do ambiente; depois disso, vale o que está no banco, mesmo que o ambiente mude. Se o que está no banco for inconsistente, a aplicação não sobe e diz qual parâmetro corrigir. Quem já lê os parâmetros não muda nada.

- Tabela `business_rules` com uma única linha (garantida por restrição), uma coluna tipada por parâmetro do `BusinessRules` e a data da última alteração. Dias de trabalho como array de inteiros; horários em minutos desde a meia-noite.
- `BusinessRulesService` depende de `BusinessRulesRepository` injetado pelo token `BUSINESS_RULES_REPOSITORY`, com implementação Prisma. Interface pequena: ler a linha vigente; gravar os valores iniciais se não existir (sem sobrescrever, seguro com duas instâncias).
- Na inicialização: lê; se não existe, grava os valores do ambiente (validados pelo parser atual) e usa o que ficou gravado; valida a consistência com a mesma função do ambiente; guarda em memória.
- `current()` continua síncrono e não toca o repositório depois da inicialização.
- A variável de ambiente continua obrigatória e validada (TK-00.02). O `.env.example` passa a dizer que o banco vence o ambiente.
- Testes que constroem o `BusinessRulesService` direto passam a usar um helper de teste junto do módulo.

Fora deste ticket: edição pelo RH, atualização do cache e auditoria (TK-03.07).

## Critérios de aceite

- [x] **Dado** um banco sem linha de parâmetros, **quando** a aplicação inicia, **então** a linha é gravada com os valores do ambiente e `current()` os devolve.
- [x] **Dado** um banco com `SESSION_DURATION_MINUTES` gravado como 30 e o ambiente com 20, **quando** a aplicação inicia, **então** `current().sessionDurationMinutes` é 30.
- [x] **Dado** um banco com o início do almoço depois do fim do expediente, **quando** a aplicação inicia, **então** ela não sobe e a mensagem diz qual parâmetro corrigir.
- [x] **Dado** duas instâncias iniciando ao mesmo tempo num banco vazio, **quando** ambas gravam os valores iniciais, **então** fica uma única linha e nenhuma falha.
- [x] **Dado** a aplicação iniciada, **quando** `current()` é chamado várias vezes, **então** o repositório não é consultado de novo.
- [x] `npm run test`, `npm run test:e2e`, `npm run lint` e `npm run build` passam.

## Testes esperados

- Seam 2: `Test.createTestingModule` com `BusinessRulesRepository` em memória no token `BUSINESS_RULES_REPOSITORY`:
  - banco vazio grava os valores do ambiente e `current()` os devolve;
  - banco com valores diferentes faz `current()` devolver os do banco;
  - valores inconsistentes fazem a inicialização falhar com mensagem que cita o parâmetro;
  - `current()` não chama o repositório depois da inicialização.
- Banco (seam 3), teste automatizado em `test/`: a restrição garante uma única linha; duas gravações iniciais em paralelo com `Promise.all` não duplicam nem falham; a aplicação iniciada por `createTestApp()` num banco vazio grava os valores do ambiente de teste.
