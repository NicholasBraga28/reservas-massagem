## O que entregar

Toda requisição à API passa a ser identificada e autorizada por padrão, com a mesma regra de herança de papéis em todo o sistema. Para quem usa, a mudança visível são mensagens de 401 e 403 que dizem o que fazer; para o time, um contrato de permissões verificado por teste.

- Módulo `auth/` com identificação e autorização registradas como guards globais, depois do limite de requisições.
- Função pura de herança de papéis: `ADMIN` → `ADMIN`, `HR`; os demais só eles mesmos. A tabela de transições do atendimento passa a usá-la no lugar da conversão própria de `ADMIN` para `HR`, sem mudar o comportamento.
- `ActorResolver` por token, escolhido por `AUTH_MODE` lido do `ConfigService`: `HeaderActorResolver` (padrão, `x-user-id`, UUID validado antes do banco) e `GoogleActorResolver` (código atual movido como está, sem testes novos).
- Usuário inexistente ou não `ACTIVE` é recusado. O usuário aceito vai para a requisição como tipo pequeno e imutável (ID, papel, nome, e-mail).
- Decorators `@Public()`, `@Roles(...)` (rota vence controller; sem `@Roles`, qualquer papel identificado) e `@CurrentActor()`.
- `@Public()` em saúde e Alexa. Controllers legados trocam `@UseGuards(ActorGuard)` e `ROLES_WITH_HR_ACCESS` pelos decorators novos, sem mudar de pasta.
- Catálogo de mensagens: substituir `missingActor`, `invalidActor` e `forbidden` pelas três mensagens da tabela "Respostas de erro" da spec.
- Log de cada recusa com o `Logger` do Nest: ID do usuário (se houver), método, rota e motivo. Sem nome nem e-mail.
- Remover `ActorGuard`, `Actor`, `ROLES_WITH_HR_ACCESS` e a leitura de `AUTH_MODE` em `process.env`.
- `CLAUDE.md`, seção "Estado atual do código": remover a linha de `ROLES_WITH_HR_ACCESS`.

Fora deste ticket: `GET /me` (TK-02.02), `GET /auth/demo-users` (TK-02.03), posse do atendimento (RN-13, EP-04 a EP-07), identificação da Alexa por aparelho (EP-07).

## Critérios de aceite

- [x] **Dado** uma rota identificada, **quando** chega sem `x-user-id`, **então** responde 401 com "Você ainda não se identificou: escolha um usuário na tela de entrada."
- [x] **Dado** um `x-user-id` que não é UUID, **quando** a requisição chega, **então** responde 401 com a mensagem de identificação inválida, sem consultar o banco.
- [x] **Dado** um `x-user-id` de usuário inexistente ou inativo, **quando** a requisição chega, **então** responde 401 com a mesma mensagem de identificação inválida.
- [x] **Dado** um usuário `ADMIN`, **quando** chama uma rota `/admin/*`, **então** tem acesso (herda `HR`).
- [x] **Dado** um usuário `HR`, **quando** a função de herança verifica o papel `ADMIN`, **então** a resposta é não.
- [x] **Dado** um usuário `ADMIN`, **quando** chama uma rota `/booking/*` ou `/therapist/*`, **então** recebe 403.
- [x] **Dado** cada linha da matriz de permissões da spec (exceto `GET /me` e `GET /auth/demo-users`, que entram nos próprios tickets), **quando** cada papel e a requisição sem identificação chamam a rota, **então** o resultado é o da matriz.
- [x] **Dado** `GET /health` ou `POST /alexa`, **quando** chegam sem `x-user-id`, **então** não respondem 401.
- [x] **Dado** a tabela de transições do atendimento, **quando** o `ADMIN` pede uma transição permitida ao `HR`, **então** continua permitida, pela função de herança compartilhada.
- [x] **Dado** uma recusa 401 ou 403, **quando** é registrada no log, **então** o registro tem só ID, método, rota e motivo.
- [x] **Dado** o código-fonte, **quando** se procura `ActorGuard`, `ROLES_WITH_HR_ACCESS` ou `process.env.AUTH_MODE`, **então** não há ocorrências.
- [x] As três mensagens de erro têm teste de formato: uma frase, em português, sem "cabeçalho", "token", "x-user-id" nem código de status.
- [x] `npm run test`, `npm run test:e2e`, `npm run lint` e `npm run build` passam.
