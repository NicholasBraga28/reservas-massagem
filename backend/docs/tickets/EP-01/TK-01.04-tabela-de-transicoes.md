## O que entregar

Todas as mudanças de status das rotas legadas passam por uma única tabela de transições, pura e testada, que diz quem pode disparar cada transição. Transição fora da tabela devolve 409 com uma frase curta em português. O massoterapeuta passa a poder iniciar a sessão de quem está em `POSSIBLE_NO_SHOW`.

- Acrescentar ao módulo de estados criado no TK-01.03 (sem Nest, Prisma nem relógio):
  - a pergunta "esta transição é permitida para este ator?" (sim/não);
  - a afirmação que lança `InvalidStatusTransitionException` quando não é.
- Atores: `EMPLOYEE`, `THERAPIST`, `HR`, `ADMIN`, `SYSTEM`. `SYSTEM` não é papel de usuário. `ADMIN` é tratado como `HR`.
- As transições originalmente entregues pelo TK-01.04 estão na tabela da spec. Estados finais não têm saída; transição para o mesmo estado é inválida. A transição `CHECKED_IN` → `COMPLETED` por `SYSTEM` foi acrescentada depois pelo TK-05.05, conforme D-06. Cancelamento a partir de `CHECKED_IN`, `POSSIBLE_NO_SHOW` ou `IN_PROGRESS` fica de fora.
- O módulo não verifica posse, prazos nem horário (EP-04 a EP-06).
- `InvalidStatusTransitionException` estende `ConflictException`. Mensagem do catálogo (proposta, a validar no TK-14.03): "Esta ação não está disponível para este atendimento agora. Consulte a agenda para ver a situação dele." Estado de origem, destino, ator e ID do atendimento só no log, sem nome de pessoa (RNF-04).
- Código legado: cancelar (colaborador ou RH), check-in, iniciar e finalizar sessão consultam a tabela antes de gravar. A atualização condicional no banco continua (proteção contra concorrência).
- Auditoria das transições não é deste ticket (TK-04.08).

## Critérios de aceite

- [x] **Dado** cada linha da tabela de transições, **quando** um ator listado pede a transição, **então** ela é permitida.
- [x] **Dado** uma linha da tabela, **quando** um ator não listado pede a transição, **então** é lançada `InvalidStatusTransitionException`.
- [x] **Dado** um atendimento `CONFIRMED`, **quando** o massoterapeuta pede `IN_PROGRESS`, **então** é permitido (início sem check-in).
- [x] **Dado** um atendimento `IN_PROGRESS`, **quando** o sistema pede `COMPLETED`, **então** é permitido (RN-16).
- [x] **Dado** um atendimento `CONFIRMED`, **quando** o `ADMIN` pede `CANCELLED`, **então** é permitido, como para o `HR`.
- [x] **Dado** um atendimento em estado final (`COMPLETED`, `CANCELLED`, `RELEASED`, `NO_SHOW`), **quando** qualquer ator pede qualquer transição, **então** é lançada `InvalidStatusTransitionException`.
- [x] **Dado** um atendimento `CHECKED_IN` sem início, **quando** o sistema pede `COMPLETED`, **então** era recusado antes da decisão D-06; a transição passou a ser permitida no TK-05.05.
- [x] **Dado** um atendimento `CONFIRMED`, **quando** o colaborador pede `IN_PROGRESS`, **então** é recusado.
- [x] **Dado** qualquer estado, **quando** a transição é para ele mesmo, **então** é recusada.
- [x] **Dado** uma transição recusada, **quando** a exceção chega ao usuário, **então** a mensagem é a do catálogo, em português, em uma frase, sem nome de estado nem código.
- [x] **Dado** um atendimento `POSSIBLE_NO_SHOW`, **quando** o massoterapeuta inicia a sessão pela rota legada, **então** ela passa a `IN_PROGRESS`.
- [x] **Dado** um atendimento `CHECKED_IN`, **quando** o colaborador tenta cancelar pela rota legada, **então** recebe 409 com a mensagem do catálogo.
- [x] `npm run test`, `npm run test:e2e`, `npm run lint` e `npm run build` passam.

## Comentários

- 2026-10-20, implementação: `isTransitionAllowed` e `assertTransitionAllowed` em `src/appointments/appointment-status.ts`, `InvalidStatusTransitionException` ao lado. O ator de transição é um tipo próprio (`StatusTransitionActor`), não `UserRole | "SYSTEM"`, para que um papel novo não vire ator de transição sem passar pela tabela.
- O log da transição recusada (ID do atendimento, origem, destino e ator, sem nome de pessoa) fica no `InvalidStatusTransitionFilter` (`src/common/filters/`), registrado no `configureApp`. O módulo puro só lança a exceção, que carrega esses dados em `transition`; o corpo da resposta leva só a mensagem do catálogo (testado no `test/status-transitions.e2e-spec.ts`).
- Ordem nos services legados: posse e prazos primeiro (`assertCanCancel`, `assertCanCheckIn`), depois a tabela, como diz a spec. A atualização condicional agora usa o estado de origem lido (`status: current.status`). Quando ela perde a corrida, as mensagens antigas (`appointmentCannotCancel`, `checkInUnavailable`, `sessionCannotStart`, `sessionNotInProgress`) continuam: unificar com a mensagem da tabela fica para os services donos (EP-04, EP-05).
- Mudança de comportamento: cancelar a partir de `CHECKED_IN` ou `IN_PROGRESS` passou a 409; iniciar a partir de `POSSIBLE_NO_SHOW` passou a ser permitido.
- Cancelamento pelo RH: `BookingService.cancel` recebe o ator e já aceita `HR`/`ADMIN` (sem verificação de posse), mas o código legado não tem rota de cancelamento do RH. A rota fica para o EP-04/EP-08.
- Alexa: os intents de iniciar, finalizar e cancelar passam pela tabela via `TherapistService`, mas o `alexa.controller.ts` captura todo erro e responde com uma frase genérica, então a recusa não é logada nem falada com a mensagem do catálogo. Fica para o EP-07 (handlers de intent).
- [VALIDAR] A mensagem proposta pela spec tem duas frases ("...agora. Consulte a agenda..."), e o critério e o `CLAUDE.md` pedem uma frase. Entrou o texto da proposta, sem alteração; o teste verifica o texto do catálogo e a ausência de nomes de estado e códigos, não o número de frases. Decidir no TK-14.03.
