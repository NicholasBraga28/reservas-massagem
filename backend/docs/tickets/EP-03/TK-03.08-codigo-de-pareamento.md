- Próximos consumidores: TK-07.05 (intent "vincular código"), TK-12.06 (tela do código).

## O que entregar

O RH gera, para um massoterapeuta ativo, um código que ele diz à Alexa da sala ("vincular código {código}") para vinculá-la à própria agenda:

- `POST /therapists/:id/alexa-pairing-code`, `@Roles("HR")`, no módulo `alexa/`. Resposta `201` com `code`, `therapistId` e `expiresAt`, como na spec.
- Código numérico, único entre os não consumidos, gerado por fonte criptográfica. Em colisão, tenta de novo.
- Massoterapeuta tem de existir (404) e estar ativo (`therapistInactive`).
- `AuditEvent` da geração, sem o código. O código não vai para o log.
- Linha nova na matriz de permissões.

Fora deste ticket: consumo do código e troca de dono do aparelho (TK-07.05).

## Critérios de aceite

- [x] **Dado** um massoterapeuta ativo, **quando** o RH chama `POST /therapists/:id/alexa-pairing-code`, **então** um código numérico com o tamanho e a validade da D-18 é gravado em `AlexaPairingCode` e devolvido com `expiresAt`.
- [x] **Dado** um massoterapeuta inativo ou inexistente, **quando** o RH gera um código, **então** responde com a mensagem correspondente e nada é gravado.
- [x] **Dado** uma fonte aleatória fixada para repetir um código não consumido, **quando** o RH gera, **então** sai um código diferente.
- [x] **Dado** a geração, **quando** se consulta a auditoria, **então** o evento não contém o código.
- [x] **Dado** um colaborador ou massoterapeuta, **quando** chama a rota, **então** responde 403 (matriz de permissões).
- [x] `npm run test`, `npm run test:e2e`, `npm run lint` e `npm run build` passam.

## Comentários

- **2026-10-21 — alinhado à spec da Mariana.** A seção "Solution" da spec diz "6 dígitos **alfanuméricos**", e o contrato diz "numérico". O slot numérico da Alexa só reconhece dígitos, então a proposta é numérico; corrigir a "Solution".
- Propostas da primeira versão que **não estão na spec**, a decidir:
  - Gerar um código novo invalida os anteriores não usados do mesmo massoterapeuta (um código ativo por vez).
  - A resposta traz um `spokenText` com os dígitos separados, para o RH ler em voz alta a quem não lê a tela.
- **2026-10-22 — D-18 decidida (Guilherme).** 60 minutos, porque o RH pode gerar o código longe da sala. Gerar um código novo expira os anteriores não usados do mesmo massoterapeuta (`expires_at` = agora): um código ativo por vez. O `spokenText` ficou de fora: a rota é do painel do RH, e a leitura do código cabe à tela do TK-12.06.
- **2026-10-22 — n massoterapeutas : 1 Alexa (RN-17).** Uma mesma Alexa pode ser usada por vários massoterapeutas. Não muda este ticket (o código continua sendo de um massoterapeuta), mas contradiz o modelo do TK-01.05 (`alexa_devices.therapist_id`, um dono por aparelho) e a "troca de dono ao parear de novo" do TK-07.05. Como a Alexa sabe quem está falando virou a D-19, que bloqueia o TK-07.05.
- Códigos expirados e não usados continuam ocupando o valor no índice único parcial (`consumed_at IS NULL`); a geração sorteia de novo (até 5 tentativas) quando o valor está ocupado.
- Duas gerações simultâneas para o mesmo massoterapeuta são serializadas por um bloqueio na linha de `therapists` (`SELECT … FOR UPDATE`), para manter um código ativo por vez. O evento de auditoria registra quantos códigos anteriores foram expirados (`expiredPreviousCodes`).
